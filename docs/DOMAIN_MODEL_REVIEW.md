# Domain Model Review — Mbamager Financial Operating System

This document outlines the architectural specifications, entities, constraints, and structural design choices of the Mbamager SQLAlchemy 2.0 domain models.

---

## 1. Model Schema Definitions

### A. `User` Model
Represents registered individuals or households using the platform.

*   **Fields:**
    *   `id` (`Mapped[int]`): Primary key. Auto-incremented unique identifier.
    *   `phone_number` (`Mapped[str]`): Unique phone identifier (e.g., in ITU-T E.164 format). Max length 32.
    *   `username` (`Mapped[Optional[str]]`): Optional display name. Max length 64.
    *   `hashed_password` (`Mapped[str]`): Cryptographically secure salted password hash (Bcrypt). Max length 255.
    *   `is_active` (`Mapped[bool]`): Boolean flag denoting whether the user account is active.
    *   `created_at` (`Mapped[datetime]`): Timestamp when the user registered, automatically populated with timezone support.
    *   `updated_at` (`Mapped[datetime]`): Timestamp when the user profile was last updated, managed via database triggers.

*   **Relationships:**
    *   `financial_profile`: One-to-One (`uselist=False`) relationship back-populates to the `FinancialProfile` model. Set to cascading delete-orphan.
    *   `accounts`: One-to-Many relationship back-populates to the `Account` model. Set to cascading delete-orphan.
    *   `budgets`: One-to-Many relationship back-populates to the `Budget` model. Set to cascading delete-orphan.

---

### B. `FinancialProfile` Model
Maintains configuration variables, regional selections, and system preferences mapped to a user.

*   **Fields:**
    *   `id` (`Mapped[int]`): Primary key.
    *   `user_id` (`Mapped[int]`): Foreign key referencing `users.id`. Mapped with cascading deletion on the database level.
    *   `preferred_currency` (`Mapped[str]`): Standard ISO 4217 Currency Code. Default is `"XAF"` (Central African CFA franc). Max length 3.
    *   `language` (`Mapped[str]`): Language locale selection (e.g., `"en"`, `"fr"`). Default is `"en"`. Max length 5.
    *   `risk_tolerance` (`Mapped[str]`): Operational profile classification string (`"LOW"`, `"MEDIUM"`, `"HIGH"`). Default is `"MEDIUM"`. Max length 16.
    *   `created_at` (`Mapped[datetime]`): Record creation timestamp.
    *   `updated_at` (`Mapped[datetime]`): Record last update timestamp.

*   **Relationships:**
    *   `user`: Many-to-One back-populating relation to the `User` model.

---

### C. `Account` Model
Represents distinct financial storage channels such as mobile money wallets, banks, or physical cash reserves.

*   **Fields:**
    *   `id` (`Mapped[int]`): Primary key.
    *   `user_id` (`Mapped[int]`): Foreign key referencing `users.id`.
    *   `name` (`Mapped[str]`): User-assigned display name (e.g., "My MoMo Wallet", "Main Cash Envelope"). Max length 64.
    *   `account_type` (`Mapped[AccountType]`): Strict Enum field defining storage class (`CASH`, `MOBILE_MONEY`, `BANK`, `OTHER`).
    *   `provider` (`Mapped[AccountProvider]`): Strict Enum field defining network provider (`MTN_MOMO`, `ORANGE_MONEY`, `CASH`, `BANK`, `OTHER`).
    *   `currency` (`Mapped[str]`): Standard ISO 4217 Currency Code (default `"XAF"`). Max length 3.
    *   `is_active` (`Mapped[bool]`): Status flag of the ledger account. Default is `True`.
    *   `created_at` (`Mapped[datetime]`): Record creation timestamp.
    *   `updated_at` (`Mapped[datetime]`): Record last update timestamp.

*   **Relationships:**
    *   `user`: Many-to-One back-populating relation to the `User` model.
    *   `transactions`: One-to-Many relation to the `Transaction` model. Configured with cascading delete-orphan.

---

### D. `Transaction` Model
Represents historical state changes and ledger adjustments. Fully decoupled from calculated asset valuations.

*   **Fields:**
    *   `id` (`Mapped[int]`): Primary key.
    *   `account_id` (`Mapped[int]`): Foreign key referencing `accounts.id`.
    *   `amount` (`Mapped[Decimal]`): Precise numerical representation of the transaction value.
    *   `fee` (`Mapped[Decimal]`): Precise numerical representation of commissions or cash-out charges paid to network providers.
    *   `direction` (`Mapped[TransactionDirection]`): Strict Enum field classifying flow direction (`CREDIT` for cash inflows, `DEBIT` for cash outflows).
    *   `category` (`Mapped[TransactionCategory]`): Strict Enum field classifying system categories (reusing central categories from constants).
    *   `narrative` (`Mapped[Optional[str]]`): User comments, SMS descriptions, or AI summaries. Max length 255.
    *   `tx_id_external` (`Mapped[Optional[str]]`): Optional transaction reference string generated by telecom operators (e.g. MTN MoMo TxID). Max length 64.
    *   `timestamp` (`Mapped[datetime]`): Official local time when the transaction actually occurred.
    *   `created_at` (`Mapped[datetime]`): Internal record creation timestamp.
    *   `updated_at` (`Mapped[datetime]`): Internal record last update timestamp.

*   **Relationships:**
    *   `account`: Many-to-One back-populating relation to the `Account` model.

---

### E. `Budget` Model
Defines spending limits and boundaries assigned over targeted periodic intervals.

*   **Fields:**
    *   `id` (`Mapped[int]`): Primary key.
    *   `user_id` (`Mapped[int]`): Foreign key referencing `users.id`.
    *   `category` (`Mapped[str]`): Standardized system category bound to this budget allocation. Max length 64.
    *   `limit_amount` (`Mapped[Decimal]`): Precise numerical budget threshold representation.
    *   `start_date` (`Mapped[date]`): Calendar date from which the budget is active.
    *   `end_date` (`Mapped[date]`): Calendar date at which the budget interval expires.
    *   `created_at` (`Mapped[datetime]`): Record creation timestamp.
    *   `updated_at` (`Mapped[datetime]`): Record last update timestamp.

*   **Relationships:**
    *   `user`: Many-to-One back-populating relation to the `User` model.

## 2. Enums, Indexes, and Constraints

### A. Python Enums (Mapped to PostgreSQL)
1.  **`AccountType`**: String-backed enum specifying `CASH`, `MOBILE_MONEY`, `BANK`, or `OTHER`. This allows multi-channel categorization.
2.  **`AccountProvider`**: String-backed enum specifying network provider (`MTN_MOMO`, `ORANGE_MONEY`, `CASH`, `BANK`, `OTHER`).
3.  **`TransactionDirection`**: String-backed enum specifying `CREDIT` (cash in) or `DEBIT` (cash out) for deterministic value addition or subtraction.
4.  **`TransactionCategory`**: String-backed enum specifying system categories, imported from central constant categories for maximum consistency.

### B. Indexes
*   `ix_users_id` on table `users` (`id`).
*   `ix_users_phone_number` on table `users` (`phone_number`) — *Unique Index* to guarantee login identifier uniqueness and accelerate lookups during session creation.
*   `ix_financial_profiles_id` on table `financial_profiles` (`id`).
*   `ix_financial_profiles_user_id` on table `financial_profiles` (`user_id`) — *Unique Index* supporting clean 1-to-1 mappings.
*   `ix_accounts_id` on table `accounts` (`id`).
*   `ix_accounts_user_id` on table `accounts` (`user_id`) to optimize querying user wallets.
*   `ix_transactions_id` on table `transactions` (`id`).
*   `ix_transactions_account_id` on table `transactions` (`account_id`) to accelerate account ledger fetches.
*   `ix_transactions_category` on table `transactions` (`category`) to optimize categorization aggregates.
*   `ix_transactions_tx_id_external` on table `transactions` (`tx_id_external`) to prevent duplicate parsing of external network logs.
*   `ix_budgets_id` on table `budgets` (`id`).
*   `ix_budgets_user_id` on table `budgets` (`user_id`).
*   `ix_budgets_category` on table `budgets` (`category`).

### C. Integrity Constraints
*   **Foreign Keys with `ondelete="CASCADE"`**: Mapped on all dependent tables (`financial_profiles`, `accounts`, `transactions`, `budgets`). If a `User` or `Account` is purged, dependent records are automatically cleaned up at the engine level to prevent database pollution.
*   **Unique Constraints**: `phone_number` in `users` must be unique. The `user_id` in `financial_profiles` is declared unique to strictly enforce a 1:1 user preferences boundary.

## 3. Nullability Audit

To preserve strict ledger sanity, nullability is minimal:
*   `User.username` is **Nullable** (`Optional[str]`) because a user may register with only their phone number in informal cash-dominant markets.
*   `Transaction.narrative` is **Nullable** (`Optional[str]`) as quick ledger captures or unstructured raw messages might lack user comments or notes.
*   `Transaction.tx_id_external` is **Nullable** (`Optional[str]`) because manual cash transactions lack telecom provider references or network identifiers.
*   All core IDs, numeric boundaries, amounts, limits, types, and timestamps are strictly **Non-Nullable** to prevent parsing crashes or partial transactions.

---

## 4. Financial Precision Audit

*   **Data Types**: Python's `decimal.Decimal` is mapped to SQL's `Numeric` type with defined scale parameters to prevent precision degradation from binary representation limits of IEEE 754 float types.
*   **Scale Configuration**: All monetary variables are mapped using `Numeric(precision=18, scale=2, asdecimal=True)`.
    *   `Transaction.amount`: Preserves exact monetary transaction value.
    *   `Transaction.fee`: Stores exact provider cash-out/commission fees.
    *   `Budget.limit_amount`: Sets precise expenditure budget limits.

## 5. Architectural Verification

### 🚫 Does Account Store a Balance?
**No.** The `Account` model contains *zero* fields tracking historical, active, or current balances. Balance computations are transient and performed on-demand or compiled dynamically inside deterministic Python service layers using transactional credits/debits. This prevents stale states and write conflicts.

### 📊 Single-Entry vs. Double-Entry Bookkeeping
Mbamager utilizes a **modified single-entry ledger structure with strict directional qualifiers (`CREDIT`/`DEBIT`)**.
*   **Reasoning**: Users in target underbanked regions are logging transactions to self-contained separate wallets (mobile wallets, personal cash boxes, or banks) rather than sending inter-account double-entry transfers.
*   **Future Adaptation**: The platform easily supports double-entry matching at the service layer by processing two paired transactions (a `DEBIT` on Source Account A and a matching `CREDIT` on Destination Account B) sharing a single reference indicator in `tx_id_external`.

## 6. Assumptions and Extensibility Design

1.  **Multi-Currency Support**: By attaching currency ISO strings to individual `Account` and `FinancialProfile` entities instead of hardcoding global properties, Mbamager is ready to expand seamlessly beyond Central African CFA (XAF) to West African CFA (XOF), Nigerian Naira (NGN), East African Shillings (KES), or US Dollars (USD).
2.  **Strongly Typed Provider Enum**: The `Account.provider` property is configured as a strongly typed `AccountProvider` enum. This constraint was intentionally selected for the MVP to improve data consistency, enforce validation rules, and prevent provider name spelling variations. Future international expansion can be achieved by extending the enum with additional regional providers (e.g., M-Pesa, Wave). A future major version may replace this enum with a dedicated Provider database entity if dynamic, runtime-driven provider management becomes necessary.
3.  **Local Dynamic Category Mapping**: Categories are saved as strings in `Transaction` and `Budget` models, enabling localized, dynamic translation mapping at the frontend layer depending on selected regional profiles.
